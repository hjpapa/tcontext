## 0. 핵심 결정 요약 (권장안)

1. **이력은 지금의 로컬 기록 안에 넣는다.**
   - 기록 형식을 v2로 올리고 `history`(이전 확정본, 최대 5개)와 `exports`(내보내기 기록)를 더한다.
   - Phase 1에 만들어 둔 마이그레이션 장치(`RECORD_UPGRADES`)를 그대로 쓴다. IndexedDB 버전은 올리지 않는다.
   - 한 기록 안에 있으므로 쓰기가 원자적이다. 기록을 지우면 이력도 함께 지워진다.
2. **버전은 "확정본이 바뀔 때만" 생긴다.**
   - 확정 저장(`saveConfirmed`)에서만 이전 확정본이 이력으로 내려간다. 초안 자동 저장은 버전을 만들지 않는다.
   - 내용이 같으면 새 버전을 만들지 않는다. 같은지는 전체본 Markdown이 같은지로 판단한다.
3. **복원은 "지난 확정본을 현재 확정본으로 되돌리기"다.**
   - 지금 확정본은 이력에 남으므로 되돌릴 수 있다.
   - 개인정보 검사를 다시 하지 않는다. 그 버전은 이미 검사와 교사 확인을 거쳤다.
   - 편집 중인 초안이 있으면 복원하지 않는다.
4. **비교는 기존 `diffProfiles`를 다시 쓴다.** 영역 단위로 "이전 / 현재"를 나란히 보여 준다. 글자 단위 diff는 하지 않는다.
5. **내보내기 기록은 형식·버전·시각만 남긴다.**
   - 내용과 모듈 선택 상태는 남기지 않는다.
   - 대상(결과 화면, 가이드 id)마다 최근 1건만 둔다.
   - 확정본이 바뀐 뒤 이전 버전을 내보낸 대상이 있으면 "교체하세요"를 안내한다(지침서 6.3).
6. **skill 패키지는 `SKILL.md` 안에 핵심본 2.0을 넣는다.**
   - Gemini 실측에서 참고 파일을 읽지 않고 답한 문제가 있었다. 공개 사양상 참고 파일은 필요할 때만 읽힌다.
   - 그래서 핵심 맥락을 skill이 켜질 때 항상 읽히는 `SKILL.md`에 둔다. 전체본은 지금처럼 `references/teacher-profile.md`에 남긴다.
7. **호환성 검사는 공개 Agent Skills 사양을 기준으로 하는 범용 검사기다.**
   - 플랫폼별 차이(요금제, 메뉴, 코드 실행 필요 여부)는 가이드 콘텐츠에만 쓴다.
   - ChatGPT·Claude에도 skill 설치 안내를 추가한다.
8. **바꾸지 않는 것**: 전체본·핵심본·모듈 선택본 출력, JSON 백업 형식, 기여·관리자 대조, 서버.

### 1.2 저장 구조 현황

- DB `tcontext-local-profiles` v1, 저장소 `profiles`(기록)와 `meta`(설정)

- 동시성: 내용 쓰기마다 `revision`을 올리고 `expectedRevision`으로 충돌을 잡는다.

## 2. 버전 이력 (과제 D)

### 2.1 기록 형식 v2

```ts
// v1 필드는 모두 그대로 둔다.
storageSchemaVersion: 2,
history: Array<{
  profile: TeacherContextProfile;   // 이전 확정본. 검사 대기 상태 불가
  confirmedAt: string;              // 그 버전을 확정한 시각 = 버전 식별자
  replacedAt: string;               // 현재 확정본에서 내려온 시각
}>,                                 // replacedAt 내림차순, 최대 MAX_PROFILE_HISTORY(5)
exports: Array<{
  target: string;                   // "result" 또는 가이드 id. 소문자·숫자·하이픈
  format: "full" | "core" | "modules" | "skill-package";
  confirmedAt: string;              // 내보낸 버전의 confirmedAt
  exportedAt: string;
}>,                                 // target당 1건, 최대 10건
```

- 검증
  - 이력 항목도 확정본과 같은 규칙을 따른다: 스키마 검증, 지원 버전, 검사 대기 상태 불가
  - `confirmedAt`은 현재 확정본과 이력 전체에서 겹치지 않는다.
  - 이력이 있으면 확정본도 있어야 한다.
  - `exports`는 형식만 검사한다. 내보낸 버전이 보관 범위(5개)를 벗어나 사라져도 기록은 남는다.
- 대상 id는 불투명한 문자열이다. 저장 계층의 코드에는 플랫폼 이름을 쓰지 않는다(아키텍처 가드 유지).
- 설정 레코드(`meta`)의 형식은 바꾸지 않는다. 기록과 설정의 버전 상수를 나눈다.

### 2.2 버전이 생기는 규칙

- **확정 저장할 때만** 생긴다. `saveConfirmed`가 이 규칙을 한곳에서 처리하므로, 화면 쪽 호출부는 바뀌지 않는다.
  - 호출하는 곳: 검토 완료(자동 저장 `finalize`), 결과 화면의 저장 패널, 충돌 시 덮어쓰기
- 처리 순서(한 트랜잭션 안)
  1. 새 확정본과 현재 확정본이 **같은 내용**인지 본다.
     - 같음: 이력을 만들지 않는다. 확정본의 `profile`만 새 값으로 바꾸고 `confirmedAt`은 그대로 둔다. 초안 비우기와 태그 병합은 지금처럼 한다.
     - 다름: 현재 확정본을 `{ profile, confirmedAt, replacedAt: now }`로 이력 맨 앞에 넣는다. 새 확정본을 현재로 둔다.
  2. 이력이 5개를 넘으면 가장 오래된 것(`replacedAt`이 가장 이른 것)을 지운다.
- 같은 내용일 때도 확정본의 `profile`은 새 값으로 바꾼다. 분석 태그(`confirmedTags`)처럼 Markdown에 나오지 않는 수정이 사라지지 않게 하기 위해서다. `confirmedAt`만 유지한다.
- "같은 내용" = 두 프로필의 전체본 Markdown이 같다.
  - 교사에게 전달되는 내용이 같으면 같은 버전으로 본다. 분석 태그나 개인정보 검사 항목의 세부만 다른 경우는 새 버전을 만들지 않는다.
  - WU-16a의 기준 시점 판정과 같은 기준이다.
  - 함수는 `src/lib/profile/versions.ts`의 `sameProfileContent(a, b)` 하나로 두고, 저장소와 화면이 함께 쓴다.

### 2.3 마이그레이션

- `RECORD_UPGRADES[1]`: v1 기록에 `history: []`, `exports: []`를 더하고 `storageSchemaVersion: 2`로 바꾼다.
- 읽을 때 변환하고, 다음 쓰기에서 v2로 저장된다. 읽기만으로는 DB를 고치지 않는다(현행 방식 유지).
- 되돌림 위험: v2 기록을 이전 코드가 읽으면 `unsupported_version`으로 표시되고 지워지지 않는다(현행 보호 장치).

### 2.4 저장소 API

| 함수                                                          | 종류           | 동작                                            |
| ------------------------------------------------------------- | -------------- | ----------------------------------------------- |
| `saveConfirmed`(기존)                                         | 내용 쓰기      | 2.2 규칙 추가. 시그니처 그대로                  |
| `restoreVersion(id, { confirmedAt, expectedRevision })`(신규) | 내용 쓰기      | 2.6                                             |
| `deleteVersion(id, { confirmedAt })`(신규)                    | 부가 정보 쓰기 | 이력 항목 하나 삭제. 현재 확정본은 지울 수 없다 |
| `recordExport(id, { target, format, confirmedAt })`(신규)     | 부가 정보 쓰기 | 대상별로 최근 1건 갱신. 최대 10건               |

- **내용 쓰기**는 지금처럼 `expectedRevision`을 확인하고 `revision`과 `updatedAt`을 올린다.
- **부가 정보 쓰기**는 `revision`과 `updatedAt`을 바꾸지 않는다.
  - 내보내기 한 번 때문에 다른 탭의 편집이 충돌하거나 목록 순서가 바뀌면 안 되기 때문이다.
  - 트랜잭션 안에서 최신 기록을 읽어 그 필드만 고쳐 쓴다. 다른 필드를 덮어쓰지 않는다.
- 모든 기존 쓰기(`saveDraft`, `discardDraft` 등)는 트랜잭션 안에서 읽은 기록을 고쳐 쓰므로 `history`와 `exports`를 보존한다. 테스트로 고정한다.

### 2.5 비교와 바뀐 영역

- `diffProfiles(이전, 이후)`를 그대로 쓴다(검토 화면의 변경 배지와 같은 함수).
- 버전 목록의 "바뀐 영역": 각 버전과 바로 다음(더 새로운) 버전을 비교해 바뀐 모듈 제목과 종합 섹션 이름을 보여 준다. 저장하지 않고 화면에서 계산한다.
- 비교 화면: 고른 버전과 현재 확정본을 비교한다. 바뀐 영역마다 "이전"과 "현재" 내용을 나란히(좁은 화면에서는 위아래로) 보여 준다.
  - 모듈: 제목, 요약, 문장 목록(추가·수정·삭제 표시)
  - 종합 섹션: 목록 전체
  - 개인정보 상태가 다르면 함께 표시한다.

### 2.6 복원

- 동작(한 트랜잭션)
  1. 초안이 있으면 `draft_exists`로 거절한다. 화면은 "편집 중인 초안을 확정하거나 버린 뒤 복원할 수 있습니다"를 보여 준다.
  2. 현재 확정본을 이력 맨 앞으로 내린다(`replacedAt: now`).
  3. 고른 이력 항목을 현재 확정본으로 올리고 이력에서 뺀다. **`confirmedAt`은 원래 값을 유지한다.** 그 내용을 교사가 확정한 시각이기 때문이다.
     - 그래서 핵심본의 기준 시점도 그 날짜로 돌아간다.
     - 그 버전을 내보낸 기록이 있으면 "교체 필요"가 사라진다(3.3).
  4. `revision`을 올린다. 이력 수는 바뀌지 않는다.
- 세션이 같은 기록에 연결되어 있으면 복원한 확정본을 보기 모드로 다시 연다(`openProfile`). 세션과 저장소가 어긋나지 않게 하기 위해서다.
- 개인정보 검사를 다시 하지 않는다. 그 버전의 검사 결과와 경고 상태를 그대로 쓴다.

### 2.7 저장 공간과 삭제 정책

- 기록당 이전 확정본은 최대 5개다. 넘으면 가장 오래된 것부터 자동으로 지운다.
- 교사는 이력 항목을 하나씩 지울 수 있다.
- 기록 삭제와 "모두 삭제"는 이력과 내보내기 기록도 함께 지운다(같은 기록 안에 있음).
- 저장 공간 부족(`quota_exceeded`)이 나면 기존처럼 저장하지 못했다고 안내한다. 이력 때문에 확정 저장이 실패하면 오래된 이력을 지우고 다시 시도하라고 안내한다.
- 개인정보 안내 화면과 문서에 "이전 확정본 최대 5개와 내보내기 기록(형식·시각)도 이 브라우저에 저장된다"를 추가한다.

## 3. 내보내기 기록과 교체 안내

### 3.1 기록하는 동작

| 화면           | 동작                                              | `target`  | `format`        |
| -------------- | ------------------------------------------------- | --------- | --------------- |
| 결과 화면      | 수업 설계용 Markdown 다운로드, 전체 컨텍스트 복사 | `result`  | `full`          |
| 결과 화면      | 핵심본 복사                                       | `result`  | `core`          |
| 결과 화면 패널 | 복사, Markdown 다운로드                           | `result`  | 선택한 형식     |
| AI 활용 가이드 | 교사 Markdown 다운로드                            | 가이드 id | 선택한 형식     |
| AI 활용 가이드 | skill 패키지 다운로드                             | 가이드 id | `skill-package` |

- 기록하지 않는 것: JSON 백업(외부 AI 전달이 아님), 일반 텍스트 복사, 인쇄, 지침 파일(교사 내용이 없음)
- 일반 텍스트 복사는 기록에서 빼는 것을 권장한다. 9장 결정 6에서 정한다.

### 3.2 기록 조건

- 다음을 모두 만족할 때만 기록한다. 하나라도 아니면 아무것도 남기지 않는다.
  1. 로컬 저장이 켜져 있고(`enabled`), 세션이 기록에 연결되어 있다.
  2. 내보낸 내용의 원본(세션 프로필)이 저장된 현재 확정본과 같은 내용이다(`sameProfileContent`).
  3. 복사나 다운로드가 성공했다.
- 기록할 `confirmedAt`은 그 현재 확정본의 값이다.
- 기록은 내보내기 뒤에 따로 실행한다. 실패해도 교사에게 오류를 보이지 않고 내보내기를 막지 않는다.
- 이 판정은 `useContextAsOf`(WU-16a)와 같은 기준이다. 판정 함수를 하나로 모아 두 곳이 함께 쓴다.

### 3.3 교체 안내 (지침서 6.3)

- **"교체 필요"** = 내보내기 기록의 `confirmedAt`이 현재 확정본의 `confirmedAt`과 다르다.
- 표시 위치
  - 결과 화면(연결된 기록일 때): "이전 버전을 내보낸 곳이 있습니다" 안내와 대상별 목록(대상 이름, 형식, 날짜). 각 대상에 "교체 방법 보기" 링크를 둔다(가이드 화면의 해당 방법).
  - 내 프로파일 목록: 기록마다 "최근 내보낸 기록" 한 줄과 교체 필요 표시
  - 버전 기록 화면: 대상별 기록
- 대상 이름은 가이드 콘텐츠(`PLATFORM_GUIDES`)에서 id로 찾는다. `result`는 "결과 화면에서 내보냄"으로 표시한다. 찾을 수 없는 id는 id 그대로 보여 준다.
- 가이드 콘텐츠의 방법마다 선택 필드 `updateNote`를 둔다. 예: "skill 화면에서 Replace skill로 새 zip을 다시 올립니다." 문구는 공식 문서로 확인한 것만 쓴다.
- 문구는 "내보낸 기록"이라고 쓴다. 교사가 실제로 외부 AI에 올렸는지는 TContext가 알 수 없기 때문이다.

## 4. skill 패키지 개선 (과제 E)

### 4.1 구성

```text
teacher-context.zip
└── teacher-context/
    ├── SKILL.md                    # 머리말 + 사용 지침 + 교사 핵심 맥락(핵심본 2.0 본문)
    └── references/
        └── teacher-profile.md      # 전체본(현행 그대로)
```

- 폴더 이름, `name`, 참고 파일 경로는 바꾸지 않는다. 이미 올린 skill을 같은 이름으로 교체할 수 있게 하기 위해서다.
- 모듈별 참고 파일은 만들지 않는다(9장 결정 7).
  - 전체본은 4,400~6,100자 수준(측정)이라 필요할 때 통째로 읽어도 부담이 적다.
  - 파일이 많아지면 AI가 엉뚱한 파일을 읽거나 아무것도 읽지 않을 가능성이 커진다.

### 4.2 `SKILL.md` 본문

```text
---
name: teacher-context
description: (현행 문구)
---

# 교사 컨텍스트 사용 지침

{도입 문단: 이 파일 아래쪽의 "# {프로필 제목}"부터가 교사 핵심 맥락이다. 교육 관련 요청에는 먼저 이 맥락을 적용한다.
 교사가 직접 말한 근거 문장, 모듈별 세부 내용, 수업 작업 양식이 필요하면 references/teacher-profile.md를 읽는다.
 그 파일을 읽지 못했다면 사용자에게 알리고, 핵심 맥락만으로 답했다고 밝힌다.}

{COMMON_USAGE_INSTRUCTIONS}

## 사용 원칙

- {SKILL_USAGE_PRINCIPLES}

{핵심본 2.0 출력에서 YAML 머리말을 뺀 본문 전체("# {profileTitle}"부터 끝까지)}
```

- 핵심본 본문은 **생성기 출력을 글자 그대로** 붙인다. 따로 고쳐 쓰지 않으므로 Phase 3.1의 충실성 검사가 그대로 유효하다.
- 핵심본의 머리말(`context_as_of`, `privacy_review`)은 빠지지만, 같은 정보가 본문의 기준 시점 문단과 개인정보 경고로 남는다.
- 예상 크기(측정): 1,900~~2,400자, 65~~80줄
- **크기 한도**: 본문이 500줄 또는 8,000자를 넘으면 핵심본을 넣지 않고 지금의 "참고 파일만" 방식으로 만든다.
  - 8,000자는 공개 사양의 5,000토큰 권장을 글자 수로 보수적으로 바꾼 값이다.
  - 이때 가이드 화면에 "문서가 길어 핵심 맥락을 skill 본문에 넣지 못했습니다. 대화 첨부 방식을 권장합니다"를 보여 준다.
- 기준 시점은 `useContextAsOf`로 정한다(결과 화면·가이드와 같은 값).
- 지침 전용 `SKILL.md`(`teacher-context-guide`, 대화 첨부용)는 바꾸지 않는다.

### 4.3 호환성 검사

- `src/lib/export/skill-check.ts`: `checkSkillPackage(entries)` → 문제 목록(없으면 빈 배열). 플랫폼 이름을 쓰지 않는 범용 검사다.
- 검사 항목(공개 사양 기준, 값은 `src/content/skill-format.ts`에 출처·확인 날짜와 함께 둔다)

| 항목          | 규칙                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------- |
| 폴더 구조     | 최상위 폴더가 하나이고, 모든 경로가 `{name}/`으로 시작한다. `{name}/SKILL.md`가 있다                    |
| `name`        | 1~64자, `^[a-z0-9]+(-[a-z0-9]+)*$`, 폴더 이름과 같다                                                    |
| `description` | 1~1024자                                                                                                |
| 머리말 필드   | 사양에 있는 필드만 쓴다(`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`) |
| 본문 크기     | 500줄, 8,000자 이내                                                                                     |
| 참고 파일     | `SKILL.md`가 언급한 `references/…` 파일이 모두 있고, 한 단계 깊이다                                     |

- 검사는 다운로드 직전에 실행한다.
  - 통과하면 skill 다운로드 옆에 "공개 Agent Skills 형식 검사 통과"를 보여 준다.
  - 실패하면 다운로드를 막고 문제를 보여 준다. 정상 입력에서는 실패하지 않아야 하며, 테스트로 고정한다.
- 플랫폼별 조건(요금제, 코드 실행, 관리자 설정)은 검사 대상이 아니다. 가이드의 `availabilityNote`로 안내한다.

### 4.4 플랫폼 안내 보강

| 플랫폼  | 방법                  | 상태        | 핵심 안내                                                                                                                                       |
| ------- | --------------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude  | `claude-skill`(신규)  | `available` | Customize > Skills > + > Create skill > Upload a skill로 zip 업로드. **코드 실행이 켜져 있어야 함.** Team·Enterprise는 관리자가 막을 수 있음    |
| ChatGPT | `chatgpt-skill`(신규) | `available` | Business·Enterprise·Healthcare·Edu 전용(워크스페이스 설정에 따름). Plugins > Skills > Create > Upload from your computer. 업로드 후 검사를 거침 |
| Gemini  | `gemini-skill`(기존)  | 현행 유지   | `SKILL.md`에 핵심 맥락이 들어가므로 참고 파일 문제를 줄일 수 있다. 실측 전까지 권장 경로는 대화 첨부로 둔다                                     |

- 각 방법에 `updateNote`(3.3)를 쓴다.
- ChatGPT는 업로드 파일 형식이 공식 문서에 없다. 실측(9장 결정 8) 전까지 안내에 "zip 업로드가 되지 않으면 대화 첨부 방식을 쓰세요"를 붙인다.
- `platform-facts.md`에 7절(skill 공식 사양, 2026-10-30)을 추가한다.
- 렌더러에 플랫폼 이름 분기를 넣지 않는다(현행 규칙).

## 5. 화면 설계

### 5.1 내 프로파일 목록 (`/profiles`)

- 기록마다 다음을 추가한다.
  - "처음 저장 {createdAt}"
  - "버전 {1 + history.length}개" + **버전 기록** 링크
  - "최근 내보낸 기록: {대상} · {형식} · {날짜}"와 교체 필요 표시(3.3)
- 기존 버튼(보기, 수정, 초안 버리기, 삭제)은 그대로 둔다.

### 5.2 버전 기록 (`/profiles/versions?record={id}`)

- 기록 id는 무작위 UUID이고 이 브라우저에만 의미가 있다. 개인정보가 아니다.
- 로컬 저장이 꺼져 있거나 기록이 없으면 "기록을 찾을 수 없습니다"와 내 프로파일 링크를 보여 준다. DB를 새로 만들지 않는다(`openExisting`).
- 목록(최신순)
  - **현재 확정본**: 확정 시각, 바뀐 영역(직전 버전 대비)
  - **이전 버전**: 확정 시각, 사용 기간(~`replacedAt`), 바뀐 영역
  - 버튼: **현재와 비교**, **이 버전으로 복원**, **삭제**(이전 버전만)
- 비교: 같은 화면 안에서 펼친다(2.5). 바뀐 곳이 없으면 "현재 확정본과 내용이 같습니다"를 보여 준다.
- 복원: 확인 대화상자를 거친다.
  - 설명: "이 버전을 현재 확정본으로 되돌립니다. 지금 확정본은 버전 기록에 남습니다."
  - 초안이 있으면 버튼을 비활성화하고 이유를 보여 준다.
- 삭제: 확인 대화상자를 거친다(파괴적 동작 스타일).
- 내보내기 기록: 대상별 목록과 교체 필요 표시

### 5.3 결과 화면 (`/result`)

- 연결된 기록에 "교체 필요" 대상이 있으면 3.3의 안내를 저장 패널 근처에 보여 준다.
- 내보내기 동작(3.1)이 성공하면 기록한다. 화면 문구는 바뀌지 않는다.

### 5.4 접근성·모바일

- 비교의 "이전 / 현재"에는 보이는 제목을 붙인다. 색만으로 차이를 표시하지 않는다(추가·수정·삭제 글자 배지).
- 320px에서 가로 넘침이 없어야 한다. 비교는 위아래로 쌓는다.
- 대화상자는 기존 `ConfirmLocalAction` 패턴을 쓴다.

## 6. 개인정보와 계약

- 이력과 내보내기 기록은 로컬 저장에 동의한 기록에만 생긴다. 동의하지 않은 사용자에게는 아무것도 저장하지 않는다.
- 내보내기 기록에는 내용, 모듈 선택, 외부 서비스 계정 정보를 남기지 않는다. 형식·버전·시각·대상 id만 남긴다.
- 이력 항목도 확정본과 같은 허용 목록 직렬화를 거친다. 원문 답변, 서명 토큰, 경고 확인 상태는 들어가지 않는다.
- 백업 형식, 기여 데이터, 서버는 바뀌지 않는다.
- 외부 서비스에 자동으로 올리지 않는다(지침서 8장).

| 기존 쓰기가 이력을 지움                    | 모든 쓰기 함수 뒤에 `history`·`exports` 보존                                                     |
| 같은 내용 재확정으로 이력이 쌓임           | 같은 내용 → 이력 0건, `confirmedAt` 유지                                                         |
| 이력이 5개를 넘음                          | 6번 확정 → 가장 오래된 것부터 삭제                                                               |
| 내보내기가 편집 충돌을 일으킴              | `recordExport`·`deleteVersion` 뒤 `revision`·`updatedAt` 불변, 다른 탭 초안 저장 성공            |
| 초안이 있는데 복원됨                       | `draft_exists` 거절                                                                              |
| 복원 후 세션과 저장소 불일치               | 연결된 세션이 복원본 보기로 다시 열림                                                            |
| 저장하지 않은 수정본이 "내보냄"으로 기록됨 | 내용이 다르면 기록 0건                                                                           |
| skill 본문이 핵심본과 달라짐               | `SKILL.md` 끝부분 = 핵심본 본문(글자 단위). 참고 파일 = 전체본                                   |
| 너무 긴 문서로 skill이 커짐                | 한도 초과 → 참고 파일 방식으로 전환, 안내 표시                                                   |
| 호환성 검사 회귀                           | 정상 패키지 통과, 규칙별 실패 사례(이름 규칙, 폴더 불일치, 설명 길이, 누락 참고 파일, 본문 초과) |
| 플랫폼 이름이 핵심 로직에 들어감           | 아키텍처 가드(기존) 통과                                                                         |

- E2E(chromium·mobile, 재시도 0, 프로덕션 서버)
  1. 저장 → 수정 → 확정 → 버전 기록에 2개, 바뀐 영역 표시 → 비교에 이전/현재가 보인다.
  2. 이전 버전 복원 → 현재가 바뀌고 이력 수 유지 → 결과 화면의 기준 시점이 원래 확정일
  3. 초안이 있으면 복원 버튼이 비활성화된다.
  4. 결과 화면에서 핵심본 복사 → 목록에 내보내기 기록 → 수정·확정 → 결과 화면에 교체 안내
  5. skill zip: `SKILL.md`에 핵심 맥락이 있고 참고 파일은 전체본이다. 검사 통과 표시가 보인다.
  6. v1 기록을 넣은 DB로 앱을 열어도 목록·보기·수정이 동작한다.
  7. 저장에 동의하지 않으면 DB가 생기지 않는다(기존).
  8. 320px 넘침 없음, 키보드로 비교·복원 대화상자 조작

## 9. 확정된 결정 사항 (2026-10-30)

1. **이력 저장 위치**: **확정: 기록 안 배열(v2 마이그레이션).** 별도 저장소는 DB 버전을 올리고 삭제·백업과의 정합을 따로 맞춰야 한다.
   - 구현 영향: Phase 1 테스트 일부가 "현재 기록 버전 = 1", "미래 버전 = 2"를 고정하고 있다. 버전 숫자와 새 필드만 바꾸는 기계적 변경을 runbook 3.3에 승인된 예외로 나열한다.
2. **보관 개수**: **확정: 이전 확정본 5개.** 용량은 작지만, 목록이 길어지면 교사가 고르기 어렵다.
3. **복원 방식**: **확정: 바로 현재 확정본으로 되돌리기(원래 확정 시각 유지).**
   - 대안: 초안으로 가져와 다시 검토. 개인정보 검사를 다시 거쳐야 해서 느리고 서버 호출이 생긴다.
4. **초안이 있을 때 복원**: **확정: 막는다.** 초안의 기준(`baseConfirmedAt`)이 어긋나는 것을 피한다.
5. **백업 형식**: **확정: 현행 유지(현재 버전 하나).** 이력까지 담으려면 백업 형식 v2와 가져오기 규칙이 필요하다.
6. **내보내기 기록 범위**: **확정: 대상별 최근 1건, 형식·버전·시각만 기록.** 일반 텍스트 복사와 JSON 백업은 기록하지 않는다.
7. **skill 참고 파일**: **확정: `SKILL.md`에 핵심본을 넣고 참고 파일은 전체본 하나.**
   - 대안: 모듈별 참고 파일 7개 추가. 지침서 7.3 "필요한 모듈만 읽기"에 더 가깝지만, 파일이 많아질수록 읽지 않을 위험이 커진다.
8. **ChatGPT·Claude skill 안내 추가**: **확정: 추가한다.**
   - Claude: 공식 문서에 zip 구조가 명시되어 있어 `available`로 둔다.
   - ChatGPT: 업로드 형식이 공식 문서에 없다. 사용자 실측 없이 `available`로 두고 "업로드가 안 되면 대화 첨부 방식을 쓰세요" 안내를 붙인다.
   - Gemini: 구현 뒤 사용자가 새 `SKILL.md`로 다시 실측한다. 결과에 따라 권장 경로를 다시 정한다.
9. **학교급·역할·교과(메타데이터) 수정**: **확정: Phase 4에 넣지 않는다.**
   - 지침서 6.3의 예시(담당 학년, 학급 환경, 기자재, 수업 조건)는 모듈 문장이라 지금도 고칠 수 있다.
   - 학교급·역할은 파일명·라벨·인터뷰 문항과 얽혀 있어 별도 설계가 필요하다.
